# Driver and bridge compatibility audit — Windows and Linux

Audit of commit `51fca6af3cf174db4c24e16a91a4b7f9a31f770`, 2026-11-27. Static code inspection only; no hardware, live SteamVR session, or runtime tests were available for this audit. The prompt's report block is a placeholder: no real bug report or log was supplied. Classifications distinguish a code fact from the behavior it might cause on a particular machine. Severity reflects impact if the relevant path is exercised, not a claim that every setup hits it.

**Architecture correction:** the bridge does not capture the desktop or encode the VR stream. SteamVR renders eye textures to the **driver**, which composes and encodes H.264; UDP carries it directly to Android, where MediaCodec decodes and OpenGL/Cardboard renders. The bridge is the control plane, with an optional local FFmpeg preview. There is no DXGI desktop duplication, X11 desktop capture, Wayland/PipeWire portal capture, or PC-side driver video decoder in these video paths. Consequently a portal limitation cannot be inferred merely from a black screen. This distinction is essential for the checklist below.

### Real code-path inventory

1. **Settings and detection:** primary UI `bridge/crates/cardboard-bridge/ui/app.slint` (Stream encoder chips) → `src/main.rs` apply callback → `src/core.rs:AppCore::apply_settings` → `src/net/driver.rs:send_config/config_wire_packets`: sends `CARDBOARD_CAP` and `BRIDGE_CFG` UDP. `driver_cardboardplusplus/src/Discovery.cpp:HmdDriver::DiscoveryThreadFunc` dispatches to `EncoderSetup.cpp:HmdDriver::ApplyHardwareCap/ApplyBridgeCfg/ApplyEncoderSettings`. The separate `bridge-ui` crate also has an SHM settings UI (`bridge/crates/bridge-ui/src/main.slint`, `main.rs`), rather than another video backend.
2. **Acquisition:** Windows `DirectMode.cpp:HmdDriver::CreateSwapTextureSet`, `SubmitLayer`, `Present`, `AcquireSyncTexture`, `EnsureLayerCopies`: SteamVR direct mode, D3D11 shared textures, keyed mutex and private eye copies. Linux `DirectModePosix.cpp:CreateSharedEye`, `HmdDriver::CreateSwapTextureSet`, `SubmitLayer`, `Present`, `AcquireSyncTexture`: SteamVR IPC opaque FD Vulkan images. Neither is desktop screen capture. On both, `HmdDriver.cpp:HmdDriver::InitializeVulkan` and `VulkanContext.cpp:VulkanContext::Initialize` select the device and extensions.
3. **Composition / conversion:** `EncodingThread.cpp:HmdDriver::EncodingThreadFunc/EncodePendingFrame` → `VideoEncoderShaders.cpp:VideoEncoder::ComposeSBSGPU/ReadbackToBuffer` → `VulkanCompose.cpp:VulkanCompose::Setup/FindOrImportEye/Compose/ToNv12/CopyToHost`. Vulkan renders SBS and normally writes host-visible NV12; if the NV12 compute path fails, host BGRA + `VideoEncoderFFmpeg.cpp:VideoEncoder::SwsConvert` is attempted. Failure of Vulkan composition itself drops the frame; no D3D or CPU composition fallback exists despite the stale queue-submit log.
4. **Encoder:** `VideoEncoderFFmpeg.cpp:VideoEncoder::InitializeFFmpeg` probes registered FFmpeg codecs and opens them in the matrix order; codec open failure advances to the next candidate including x264. `ConvertFrame`, `SendFrameToEncoder`, `ReceiveEncodedPackets` submit NV12, drain H.264 and optionally prepend cached SPS/PPS. This is H.264 only, not HEVC/AV1 negotiation. `EncoderSetup.cpp:SanitizeEncoderDims/ClampEncoderToCap` apply size restrictions.
5. **Transport:** `UdpTransport.cpp:HmdDriver::OnEncodedPacket/SendFannedOut` sends Annex-B locally and a four-byte length-prefixed copy to the phone, with UDP chunking; `Discovery.cpp` handles discovery/control and keyframe requests. These are separate from the bridge SHM telemetry/settings interface. Both wire contracts are shared interfaces.
6. **Decoders and renderers:** `cardboardplusplus-android/src/main/java/com/google/cardboard/video/DecoderCapabilityReporter.java:queryDecoderCapability/capOf` probes AVC limits; `VideoDecoder.java:feedDirect/feedFrame/configureLocked` uses `MediaCodec.createDecoderByType("video/avc")`, a `Surface`, and reconfigures on SPS change. It does not explicitly require a hardware decoder. Native `cardboardplusplus-android/src/main/jni/cardboardplusplus_app.cc:CreateVideoTexture/OnDrawFrame` uses SurfaceTexture/OES and Cardboard/OpenGL. Encoded input is copied in `feedDirect`; the decoded surface avoids an application CPU image copy, not necessarily all internal copies. The bridge `core.rs:AppCore::start_preview_decode` starts a separate FFmpeg H.264 process and reads scaled RGBA. No PC GPU-vendor-specific decode implementation is selected by the driver.
7. **What works in code:** codec open failures progress to the next candidate, including software; frame dimensions are aligned down to 16, FPS and bitrate are bounded; phone SPS changes trigger decoder reconfiguration; Windows uses bounded keyed-mutex waits; compute-NV12 failure attempts CPU conversion; logs record FFmpeg versions, selected codec, some init errors, and the Vulkan device name. These are implemented mechanisms, not hardware verification.

## 3. Ranked fix plan

1. **Linux video viability and safety (blocker / broad impact):** F01 correct VAAPI frame setup and first-frame fallback; F02 validate and implement SteamVR sync contract; F03 correct FD ownership and incomplete sync. Add fault-injection and Vulkan-validation tests before claiming GPU support. No wire change.
2. **Prevent lost or misleading streams (major / broad impact):** F05 correct cap-only rebuild, F06 make reconfiguration recoverable, F07/F12 add explicit init vs mid-stream recovery and device-lost handling, and F20 reject failed host copies. F21 releases failed phone codec instances. Verify IDR and phone decoder reconfiguration after fallback. F05's internal correction can preserve existing wire bytes; a richer capability message must be versioned together.
3. **Linux lifecycle and composition (major):** F04 retain resources through encode, F16 transactional swap cleanup, F10 preserve layers, F11 honor stream state. Add scene churn, teardown under load, multiple overlay and stream toggle tests on both platforms.
4. **Make choices truthful (major / broad impact):** F08 match/log devices and node identity; F09 distinguish configured vs active encoder and measured output. Add a versioned driver↔bridge capability/status exchange or coordinated SHM extension, preserving old-peer behavior; do not silently mutate locked layouts. Terse messages: “GPU encoder unavailable”, “Video unavailable”, “Restart SteamVR”.
5. **Compatibility and quality:** F13 validate phone size/rate, F14 signal and verify SDR color, F15 sandbox/node diagnostics, F19 test Vulkan requirements; handle F17 explicit API names and F18 preview errors. Any new negotiation or message fields require synchronized changes and contract tests across affected components.

No runtime code or protocol was changed by this audit. Blocker classification is conditional on the affected path; the fixes involve hardware/API behavior that cannot responsibly be validated in this environment, so they are proposed rather than guessed into production.

## 4. Diagnostics proposal and unknowns

For the hypothetical “black screen, RX 580, Wayland”, current logs can show a Vulkan device name and extensions (`VulkanContext::Initialize`), codec candidate/open messages and FFmpeg versions (`InitializeFFmpeg/LogFFmpegVersion`), some swap/compose errors, sampled NV12 mean, and configured FPS / UDP counters (`Discovery.cpp:SendBridgeStats`). They **cannot reliably** establish the selected DRM node's GPU identity, SteamVR compositor GPU, actual active codec from bridge status, portal state (none is used), every Vulkan/VAAPI/FD failure reason, decoder actually used on the phone, or whether frames reached and rendered on the phone. The configured FPS can be nonzero without working video. RX 580 hardware support, VA drivers, Steam runtime access, and Wayland behavior must be measured, not inferred from the model.

Minimal, rate-limited structured events, emitted on state changes and first failure:

- Session/versions: OS/session type and compositor, SteamVR/build, FFmpeg codec build/version, Vulkan loader/device driver version; sandbox/runtime and device-node access. Do not log personal paths or device serials by default.
- Capture path: `steamvr-direct-d3d11` or `steamvr-direct-vulkan-ipc`; first/last Submit, Present, sync-handle type, swap image format/size and failure result. Log no portal events because none occur.
